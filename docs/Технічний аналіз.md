## 1. Висновок одним абзацом

`my-lisp` уже є не просто компактним Lisp-інтерпретатором. Це **вертикальна система**, у якій одне структурне представлення поступово розширюється від S-виразів і лексичних замикань до символьного міркування, truth-maintenance, provenance, журналу знань, immutable worlds, обміну knowledge-пакетами, компіляції та FPGA-субстрату [1] [7] [9] [10] [11] [12] [13]. Найсильніша ідея проєкту — не окрема функція `eval`, не сам Lisp і не FPGA, а **єдиний перевірюваний контракт між даними, програмами, правилами, доказами й виконанням**.

Мій загальний висновок позитивний: концептуально це значно сильніший проєкт, ніж типовий «власний Lisp заради власного Lisp». Основний ризик зараз не в нестачі можливостей, а в тому, що екосистема швидко набуває кількох паралельних історичних шарів і стає важкою для зовнішнього читача та майбутнього підтримання.

## 2. Що фактично містить репозиторій

У workspace входять Rust-ядро, CLI, literate Markdown-виконання, WASM-збірка та `swarm-node` [21]. За локальною інвентаризацією checkout містить приблизно 24,9 тисячі рядків у `crates`, `lib`, тестах і скриптах. Найбільший файл стандартної symbolic-AI частини — `lib/forward.my`, приблизно 1,2 тисячі рядків; окремі шари `knowledge.my` і `world.my` мають близько 800 і 550 рядків відповідно.

Архітектуру можна подати так:

```text
Rust host / evaluator / capabilities
                │
                ▼
      core language contract
  quote atom eq car cdr cons cond
    lambda def defmacro read eval
                │
                ▼
          lib/core.my
     lists, macros, strings, maps
                │
        ┌───────┴────────┐
        ▼                ▼
   lib/unify.my      lib/forward.my
        │                │
        ▼                ▼
   lib/reason.my   TMS / JTMS / fixpoint
        └───────┬────────┘
                ▼
          lib/knowledge.my
      journal / advise / packages
                │
                ▼
            lib/world.my
    immutable snapshots / branches
                │
                ▼
     agent adapter / CLI / TCP / MCP
```

Важливе архітектурне рішення полягає в тому, що symbolic-AI шар не делегований зовнішній CLIPS-бібліотеці. `unify`, backward chaining, forward chaining і truth-maintenance вирощуються звичайним `my-lisp`-кодом поверх невеликого Rust-ядра [9] [10] [11]. Це робить систему менш зручною для швидкого production-застосування, але набагато цікавішою як дослідження мови та reasoning-машини.

## 3. Ядро мови: що зроблено добре

### 3.1. Межа між Rust і Lisp визначена свідомо

Rust відповідає за те, що справді потребує host capability або ефективної низькорівневої реалізації: reader, evaluator, арифметику, базову модель значень, файлові операції, процеси, TCP, `read`/`eval`, WASM-політику та діагностику помилок [2] [3] [4] [5] [17] [18] [19] [20]. Багато звичайних операцій — `list`, `map`, `filter`, `reduce`, `let`, `equal?`, частина string API, `quotient`, `mod`, `number->string` — живуть у `lib/core.my`, а не в Rust [7].

Це не механічне прагнення «запхати все в Lisp». У документації правильно проведена межа: якщо операція виразна в мові без неприйнятної ціни, її варто винести в бібліотеку; якщо для неї потрібна нова host capability або практична ефективність, вона може залишатися primitive [15]. Це набагато зріліший критерій, ніж просто рахувати кількість Rust-рядків.

### 3.2. Reader і data model мають правильну для Lisp основу

Reader розрізняє proper lists і dotted pairs; `(a b . c)` не зводиться до звичайного списку. Це важливо, бо без цього `read(write(value))` не є тотожним для всього простору структурних значень [5] [15]. Runtime `Value` містить `Nil`, boolean, числа, rational, рядки, символи, пари, замикання, макроси та host handles. Пара має структурну рівність, а замикання, макроси й TCP handles — identity equality [6].

`Pair` використовує `Rc`, тому `cons` є O(1), хвости можуть структурно розділятися, а глибокий `Drop` реалізований ітеративно для захисту від переповнення Rust-стека [6] [14]. Це хороша інженерна увага до поведінки пам’яті, особливо для Lisp, де довгі списки й рекурсивні обходи є звичайним сценарієм.

### 3.3. Tail calls і bootstrap не є лише декларацією

Evaluator використовує явний trampoline для останнього виразу closure і вибраної гілки `cond`; хвостово-рекурсивні програми тому не споживають Rust call stack лінійно [14]. У `core.my` list utilities переписані через `-onto`-акумулятори, а `quotient` після реального stack overflow було замінено з рекурсії за величиною частки на doubling-алгоритм із глибиною приблизно O(log(a/b)) [14]. Це важлива ознака: проєкт не тільки формулює принципи, а й реагує на конкретні failure modes.

### 3.4. Exact arithmetic є одним із найсильніших технічних компонентів

Rust-ядро має власний arbitrary-precision integer/Rational шар із base-2³² limbs, нормалізацією знака, gcd, діленням і форматуванням [17]. Операції над точними числами залишаються точними; обмеження розміру є opt-in і закінчується названою помилкою, а не тихим переходом до наближення [17].

На 16 серпня 2026 року семантику було змінено: скінченні decimal/scientific literals тепер exact за замовчуванням. Тобто `0.5` означає `1/2`, `0.1 + 0.2` означає `3/10`, а `3.0` має ту саму точну числову ідентичність, що й `3` [15] [17]. Це дуже сильний і послідовний вибір для reasoning-системи.

## 4. Self-hosting: наскільки він справжній

`lib/core.my` — це не декоративна стандартна бібліотека. У ній реально вирощені звичайні функції, макроси та частина інструментарію мови. `lib/meta-eval.my` додатково містить metacircular evaluator, який інтерпретує код як дані через alist-середовище [7] [8].

Водночас документація чесно не називає `meta-eval.my` повним self-hosting compiler або повним McCarthy evaluator. Він навмисно обмежений: не підтримує всередині себе повну семантику `def`/`defmacro`, має спрощені арності primitives і не підтримує рекурсивний top-level `def`, бо closure захоплює середовище до власного зв’язування [8].

Це не слабкість як така. Навпаки, це хороший приклад **чесно окресленої межі**. Слабкість з’явилася б лише тоді, якби README називав цей шар «повним self-hosting», не пояснюючи обмежень. Зараз код і документація в основному поводяться коректно.

| Питання | Фактичний стан |
|---|---|
| Чи є homoiconic data/code boundary? | Так: `quote`, `read`, `eval`, macros і S-expressions. |
| Чи вирощена стандартна бібліотека в Lisp? | Значною мірою так. |
| Чи є metacircular evaluator? | Так, але як окрема демонстраційна бібліотека. |
| Чи є повний self-hosting compiler? | Ні; це не слід приписувати поточному стану. |
| Чи є Rust boundary принципово поганим? | Ні; capability та exact arithmetic залишаються обґрунтовано в host. |

## 5. Symbolic reasoning: головна цінність проєкту

### 5.1. Unification

`lib/unify.my` містить логічні змінні у формі `(var name)`, substitution alist, dereferencing через `walk`, occurs-check і recursive `apply-subst` [9]. Представлення змінної як окремого структурного терма, а не як символу з домовленим префіксом, є добрим рішенням для поточного ядра, де `eq` працює тільки з атомами. Guard-перевірки перед `eq` показують, що реалізація вже пережила реальні type-error edge cases у вкладених структурах.

Особливо вдалий фрагмент — `thread-conjunction`: спільне ядро протягування стану через кон’юнкцію використовується і backward chaining, і forward chaining. Це правильна абстракція: engines відрізняються способом задоволення однієї умови, але не повинні дублювати сам алгоритм обходу conjunction [9] [10] [11].

### 5.2. Backward chaining і proof objects

`lib/reason.my` реалізує micro-Prolog-подібний пошук: goal уніфікується з head правила, body доводиться рекурсивно, а variables standardize-apart через depth-tagged names [10]. Є negation-as-failure, proof tree, `reason-explain`, usage counting та provenance.

Тут важливо розділити три різні результати:

| Поняття | Що означає в поточному рушії |
|---|---|
| **proved** | Існує знайдений proof path. |
| **cannot prove** | У поточному наборі правил пошук не знайшов доказу. |
| **false** | Саме по собі не випливає з відсутності доказу. Для цього потрібне explicit negation. |

Те, що `reason-explain` розрізняє «не доведено» і «відомо як хибне», є особливо важливим для майбутніх агентів. Це набагато краще за типову модель, у якій порожній результат або низька confidence змішує відсутність даних, суперечність і невдалий пошук.

Є один технічний недолік, який я б поставив високо в roadmap: `provenance` зараз проєктує proof-node та renamed rule, але не виглядає як повністю нормалізований proof object із фінальною substitution у кожному вузлі [10]. Для людини це часто читається нормально, але для зовнішнього агента або serializer-а локальні `(var ...)` можуть лишатися менш зрозумілими, ніж повністю instantiated statements. Я б додав до provenance поля на кшталт `bindings`, `instantiated-rule` і `children`.

### 5.3. Forward chaining і JTMS

`lib/forward.my` виростав поетапно: від single-pattern rule до fixpoint loop, потім retract, single-justification truth maintenance, multi-justification JTMS, compound conditions і quantifier-like `exists`/`forall` [11]. Це добре видно навіть із структури файлу: історія розвитку не прихована.

Сильна сторона — повний JTMS не ламає незалежне обґрунтування: якщо факт отримано двома шляхами, вилучення одного support set не повинно прибирати факт, який ще має інший support set. Однак у workspace паралельно залишилися три моделі пам’яті — `working-memory`, `justified-memory`, `jtms-memory`. Це корисно для backward compatibility та педагогічного розвитку, але створює семантичну поверхню, яку з часом буде важко тримати узгодженою.

Моя рекомендація: залишити історичні реалізації як окремі `legacy`/`teaching` modules, а для нового коду визначити одну canonical engine API. Інакше майбутній користувач не знатиме, чи має він використовувати `run`, `run-multi`, `run-tms`, `run-jtms` або `run-jtms-multi`.

## 6. Knowledge, provenance і immutable worlds

### 6.1. Knowledge journal

`lib/knowledge.my` переводить knowledge base від snapshot до append-only journal із `tell` і `retract` events. Поточний стан модуля є projection над журналом, а не окремою мутабельною копією [12]. Це добре відповідає event-sourcing-інтуїції та дозволяє розрізнити «модуль ніколи не існував» і «модуль існував, але всі його clauses були retracted».

Особливо цінні `advise` і `advise-all`. Вони перевіряють форму clause, шукають explicit opposite, повертають структуровані `accepted`, `rejected` або `conflict`, а batch-форма не залишає в журналі половину пакета після невдалої перевірки [12]. Це вже серйозніша основа для LLM-to-symbolic bridge, ніж прямий `eval` з тексту моделі.

### 6.2. Data-only interchange

Versioned `my-lisp-knowledge` envelope є правильним форматом для обміну між агентами: пакет — дані, а не код; імпорт валідовує структуру і не передає отримане в `eval` [12]. TCP transport має framing через EOF або newline receipt, що враховує split writes TCP. Водночас plain TCP — це транспорт, не security protocol: немає TLS, автентифікації чи політики довіри. Це нормально для local process або контрольованої мережі, але небезпечно подавати його як готовий міжвузловий production protocol.

### 6.3. World layer

`lib/world.my` — концептуально, можливо, найважливіше розширення. Світ має форму `(world parent journal metadata)`, кожен перехід повертає нове значення, а reasoning працює над явно переданим snapshot без читання глобального `*knowledge-journal*` [13]. Є depth, ancestor diff, common ancestor, branch diff і deterministic content address.

Це переводить систему від «агент має глобальну mutable memory» до «агент переходить між явно названими станами світу». Для відтворюваного агентного reasoning це дуже сильний фундамент. Одна й та сама ціль може мати різні, але відтворювані відповіді у двох worlds.

Поточна межа — відсутність merge policy. Divergent branches коректно повертають `World-not-ancestor`, замість вигадувати неузгоджений merge law [13]. Це правильне рішення на незавершеному етапі: краще чесно не зливати світи, ніж мовчки створювати суперечливе знання.

## 7. Чи готовий `my-lisp` для ШІ-агентів

Так, але в специфічному сенсі. Це ще не готова agent platform на кшталт «встановив і під’єднав до будь-якої моделі». Зате це дуже перспективний **formal memory and reasoning substrate**.

| Agent-потреба | Що вже є | Чого ще бракує |
|---|---|---|
| Довготривала пам’ять | Journal, modules, worlds, content identity | Стабільний зовнішній API та retrieval policy. |
| Структуровані факти | Clauses, rules, validation | Вищорівневий schema/ontology layer. |
| Перевірка висновку | Proof tree, provenance, usage counts | Повністю instantiated proof objects. |
| Безпечний ingestion | `advise`, `advise-all`, data-only packages | Політика довіри до джерел і signatures/authorship. |
| Branching/context | Immutable World, diff, ancestor | Merge/rebase semantics. |
| Tool integration | File, process allowlist, raw TCP, WASM | Stable agent/MCP adapter, timeouts, quotas, observability. |
| Нейронний інтерфейс | Концептуально передбачений controlled-language/LLM bridge | Реальний translator із typed output і refusal behavior. |

Найкраща роль Obsidian тут — людський front-end: нотатки, джерела, пояснення і ручне редагування. `my-lisp` може стати формальнішим back-end, який перетворює відібрані записи на facts/rules, перевіряє суперечності, будує proof і зберігає branchable world. Я б не робив Obsidian джерелом істини без ingestion guard; Markdown має бути input material, а не автоматично довіреним кодом.

Стабільний agent API міг би виглядати так:

```text
read-knowledge(query)
ingest-fact(module, clause, source)
advise-batch(module, clauses, source)
query(goal, world)
explain(proof-id)
provenance(statement-id)
world-diff(from, to)
branch(world)
```

Ключова ідея: MCP або HTTP має бути лише адаптером до цього контракту, а не самим ядром. Інакше протокол зовнішньої інтеграції почне визначати семантику knowledge engine.

## 8. Host capabilities і безпека

Capability discipline загалом зроблена добре. `process-run` приймає назву програми й список string arguments, ніколи не проходить через shell і працює тільки для програми, явно дозволеної в session allowlist [18]. У документації прямо пояснено, що інакше комбінація inbound TCP і process execution дала б віддалений command execution.

Але це **контроль capability, не повна OS sandbox**. Нативна збірка має `read-file`, `read-dir`, `write-file`, binary I/O, raw TCP, `load` і process execution [19] [20]. TCP listener слухає `0.0.0.0`, reads — chunked UTF-8, TLS/HTTP немає на рівні Rust. Тому для agent deployment потрібні host-level policy, firewall, timeouts, process resource limits і чітка модель довіри до vault/package/input.

Окремо варто розділяти дві речі: **отримані knowledge data** безпечно не eval-яться, але `load` навмисно виконує source forms. Це правильна семантика для мови, проте зовнішній agent adapter не повинен дозволяти перетворювати довільний network/Markdown input на `load` без окремого дозволу.

## 9. Тести, CI та документація

Репозиторій має широкий тестовий охоплення: parser/evaluator, BigInt, conformance, stack safety, CLI, meta-eval, unify, reason, forward, knowledge, advice, world, content store, TCP, WASM і swarm-node. `docs/testing.md` документує 434 passing, 0 failed і 5 ignored у зафіксованому локальному прогоні [16]. Це дуже добре як дисципліна проєкту.

Проте я не міг повторити цей прогін: у sandbox відсутній `cargo`. Тому це треба трактувати як **заявлений результат репозиторію**, а не як результат цього аудиту. GitHub Actions запускає `cargo test --workspace` і `cargo build --workspace`, що є правильним мінімумом [22]. Водночас workflow використовує `dtolnay/rust-toolchain@stable`, тобто CI не pin-ить точну версію Rust, тоді як документація описує більш відтворюваний Guix/Rust setup [16] [22]. Для language contract це важлива розбіжність.

Найпомітніший документаційний drift стосується exactness. `docs/language-core.md` досі стверджує, що decimal/exponential literals є inexact [14]. Але `docs/language-core-axioms.md` вже має explicit superseding decision від 16 серпня 2026 року: decimal/scientific literals exact by default [15]. Parser, syntax model і arithmetic code відповідають новому правилу [5] [17]. Це не просто косметична проблема: exactness є частиною language identity, тому тут має бути один canonical source, бажано executable conformance fixture плюс автоматична перевірка документаційних прикладів.

Є ще одна структурна проблема: `conformance.my` історично змішував core semantics, language contract і ecosystem library tests. Окремий tier-map і axioms document уже виправляють напрям [15] [16], але я б довів це до механічної структури: окремі `core-conformance.my`, `language-conformance.my` і `ecosystem-conformance.my`, навіть якщо вони залишаються в одному workspace.

## 10. Основні ризики

| Ризик | Серйозність | Чому це важливо |
|---|---:|---|
| Документаційна exactness-розбіжність | Висока | Читач може реалізувати неправильну мову; це порушує portability contract. |
| Кілька одночасних memory/TMS API | Висока | Новий код може обрати історичний шар і отримати іншу семантику retract/support. |
| Відсутність search/resource limits у reasoning | Висока | Recursive rules і branching можуть мати непрогнозовану глибину/час. |
| Provenance без повної instantiation | Середня-висока | Відповіді залишаються менш придатними для машинної перевірки й UI. |
| Legacy global journal поруч із immutable World | Середня-висока | Можливі дві моделі стану та складність міграції. |
| Raw TCP без auth/TLS | Висока для мережевого deployment | Протокол придатний для контрольованого local transport, але не автоматично для відкритої мережі. |
| CI на floating `stable` | Середня | Регресії можуть залежати від майбутньої версії toolchain. |
| Широкий scope workspace | Середня | Мова, symbolic AI, agent transport, hardware і swarm-node конкурують за увагу. |

Найбільш практично небезпечним є не сам алгоритм, а **відсутність явних бюджетів пошуку**. Backward chaining із recursive rules і forward fixpoint із великим fan-out мають потребувати depth limit, step limit, proof-size limit або cancellation token. Для агента це критично: модель може передати запит, який не є логічно неправильним, але обчислювально не має межі.

## 11. Рекомендований порядок наступних кроків

### P0 — узгодити executable language contract

Виправити `docs/language-core.md` і всі stale examples щодо decimal exactness. Винести conformance у три рівні або хоча б у три окремі fixture sets. CI має запускати перевірку, яка виявляє, якщо documentation examples розходяться з executable fixtures.

### P1 — визначити canonical reasoning API

Зберегти історичні `run`, single-TMS і ранні шари для навчання та compatibility, але позначити їх як legacy. Для нового коду визначити одну canonical форму rule, один canonical `run`, одну TMS semantics і один спосіб отримати proof.

### P1 — зробити proof object машинно завершеним

Кожен вузол proof має містити original goal, renamed rule, instantiated rule, final bindings, children і source metadata. Тоді `provenance` можна буде стабільно серіалізувати, показувати в UI та передавати іншому агенту без реконструкції прихованого контексту.

### P1 — додати resource-bounded reasoning

Потрібні хоча б `max-depth`, `max-steps`, `max-results` і `max-proof-nodes`. Результат перевищення межі має бути окремим structured outcome на кшталт `resource-exhausted`, а не порожнім списком.

### P2 — завершити World migration

Поступово зробити explicit `World` canonical state model, а global journal лишити compatibility layer. Далі окремо вирішити merge law: fast-forward, conflict result або explicit human/agent merge operation. Поточне рішення не merge-ити без закону є правильним; наступний крок — не додати довільний merge, а формально описати його.

### P2 — опублікувати agent adapter

Зробити маленький CLI/HTTP/MCP adapter із allowlisted operations: query, explain, ingest, export, world diff. Заборонити прямий `eval` для network input, розділити read-only і write capabilities, додати source ID, авторство, policy decision і ліміти на пакет.

### P2 — pin CI toolchain

Залишити `stable` як окремий compatibility job, але додати pinned reference job через конкретну Rust toolchain або Guix lock. Це особливо важливо для hardware/FPGA conformance, exact numbers і serialization contract.

## 12. Фінальна оцінка

`my-lisp` виглядає як **дослідницька система формальних обчислень**, що намагається повернути Lisp до його reasoning-мотивації, але не зупинитися на історичній реконструкції. Ти будуєш не «мову з дужками», а середовище, у якому можна сказати: ось факт, ось правило, ось стан світу, ось доказ, ось походження, ось інша реалізація, яка має поводитися так само.

Найцінніша властивість проєкту — **послідовність між філософією і кодом**. Це видно в exact arithmetic, data-only package import, explicit World transitions, standardizing-apart, occurs-check, JTMS і deliberate capability guards. Проєкт також має рідкісну чесність у позначенні власних меж: `meta-eval` неповний, FPGA ще не має full conformance, merge policy не вигадана, а старий TMS має відоме обмеження.

Мій технічний вердикт такий: **ядро вже достатньо серйозне, щоб бути основою для formal agent memory; головна потреба тепер — не ще більше можливостей, а консолідація контрактів, доказів і зовнішнього інтерфейсу.** Якщо зробити один canonical reasoning path, завершити proof/provenance model, додати bounded execution і прибрати документаційний drift, система стане набагато зрозумілішою зовнішньому інженерові, не втрачаючи своєї глибини.
